# Decisions (ADR log)

Append-only. Each entry: context, decision, consequences.

## 2026-10-22 · Infra: Tailscale sidecar runs in userspace mode
- **Context:** Spec §4.3 puts a `tailscale/tailscale` sidecar in front of the web container. Kernel mode needs `/dev/net/tun`, `NET_ADMIN` (and the Mealie-style examples also add `SYS_MODULE`) inside OrbStack's VM, and it rewrites routing in a network namespace that the web container shares.
- **Decision:** `TS_USERSPACE=true` with no extra capabilities or devices. Tailscale Serve terminates HTTPS for the tailnet and proxies to `http://127.0.0.1:3000` inside the shared namespace. That's the only traffic we need, and it works the same in userspace mode. Also `TS_AUTH_ONCE=true` (the auth key is used only when there's no saved state), `TS_ACCEPT_DNS=false`, and the health endpoint on `127.0.0.1:9002` only. Image pinned to `tailscale/tailscale:v1.104.2`.
- **Consequences:** Containers can't dial out to other tailnet devices. Nothing in Homebase needs to. If that changes, switch to kernel mode: `TS_USERSPACE=false`, `devices: [/dev/net/tun]`, `cap_add: [NET_ADMIN]`.
- **Status: superseded** by "Security review fixes" (below). The premise "it works the same in userspace mode" was wrong: in userspace mode tailscaled's netstack forwards inbound tailnet TCP on *any* port to `127.0.0.1:<port>`, so a peer could reach the app on `100.x:3000` (and the health endpoint on 9002) without going through Serve, with forged identity headers. The sidecar now runs in kernel mode and Next.js binds `127.0.0.2`.

## 2026-10-22 · Infra: two networks; Postgres internal-only; no published ports
- **Decision:** There are two networks. `backend` is `internal: true`, with no route out: postgres, migrate, backup, worker, tailscale (and web, through tailscale's namespace). `egress` is a normal bridge with nothing published: tailscale (so web too) and worker, which need the internet (SimpleFIN, Claude, etc.). No service has `ports:`. CI checks this with `docker compose config` and `jq`.
- **Consequences:** Postgres can only be reached from the compose network. Use `compose.sh exec postgres psql` for admin work.

## 2026-10-22 · Infra: compose is run through `infra/scripts/compose.sh`
- **Context:** `.env` lives at the repo root (per `.env.example`), but the compose file is in `infra/`, and Compose reads `.env` for `${VAR}` interpolation from the project directory.
- **Decision:** All scripts (and people) use `infra/scripts/compose.sh`, which runs `docker compose --project-name homebase --env-file <root>/.env -f infra/docker-compose.yml`. Services get secrets with `env_file: ../.env` (web, worker, migrate). Postgres, backup and tailscale get only the single variable each needs, by interpolation.
- **Consequences:** Volume names are fixed: `homebase_pgdata`, `homebase_tailscale-state`. `server-bootstrap.sh` checks for `homebase_pgdata` and refuses to generate a new DB password or master key when a database already exists.

## 2026-10-22 · Infra: images on node:24-bookworm-slim (glibc), pnpm via corepack
- **Decision:** Both Dockerfiles use `node:24.22-bookworm-slim`, not Alpine. Native addons (`argon2`, `sharp`, `esbuild`) get glibc prebuilds, and the deps stage has python3/make/g++ as a fallback. pnpm 10.34.7 is activated with corepack at build time (`COREPACK_HOME=/opt/corepack`), so `pnpm` works offline at runtime (the `migrate` service has no internet). Installs use `pnpm fetch` (lockfile-only layer) and then `pnpm install --frozen-lockfile --offline`.
- **Worker:** the image carries the full workspace install, because packages export TS source and `tsx` is a root devDependency. It runs `node --import tsx apps/worker/src/index.ts` under tini, as the non-root `node` user, with the code root-owned (read-only to the app). The one-shot `migrate` service reuses this image and runs `pnpm db:migrate`.
- **Web:** Next.js standalone output, copied with `.next/static` and `public/` into a slim runtime. Runs as `node`, `HOSTNAME=127.0.0.1`, `PORT=3000`. (Now `HOSTNAME=127.0.0.2`; see "Security review fixes".)

## 2026-10-22 · Infra: contracts for apps/web, apps/worker and packages/db
Things the app code must provide for the infra to work:
1. **apps/web next.config:** `output: "standalone"`, `outputFileTracingRoot` set to the repo root (the Dockerfile expects `apps/web/.next/standalone/apps/web/server.js` and fails the build with a clear message otherwise), `transpilePackages: ["@homebase/*" workspace packages]`, `serverExternalPackages: ["argon2"]`. `next build` must not require runtime secrets (`SKIP_ENV_VALIDATION=1` is set during the build).
2. **`GET /api/health`** (web) returns 200 only when the app can query Postgres. The Docker HEALTHCHECK and `deploy.sh` use it. The human-facing `/health` page from spec §15 is separate.
3. **Worker heartbeat:** the worker touches `/tmp/homebase-worker.heartbeat` at least every 60 s while pg-boss is healthy. The HEALTHCHECK marks it unhealthy after 3 minutes without one. `deploy.sh` only warns about the worker; it fails only on web.
4. **Backups are done by the `backup` sidecar, not pg-boss.** The `backup.pgdump` job in spec §8.1 should only check freshness: read `/backups/.last-success` (mounted read-only into the worker), and push to Alex if it's older than 26 h or `/backups/.last-failure` exists.
5. **`homebase_ro` role:** `pnpm db:migrate` must idempotently create the role `homebase_ro` and set its password from `HOMEBASE_RO_PASSWORD` (the migrate container gets the full `.env`). Restores re-create the role without a password (from `*.roles.sql`) and then re-run migrate, which sets the password again.
6. **Speech-to-text:** `WHISPER_URL` (default `http://host.internal:8178`) is a whisper.cpp server. Use `POST /inference` (multipart `file`, `response_format=json`) and `GET /health`. It decodes WAV/MP3/FLAC. iPhone `audio/mp4` needs either client-side WAV encoding or `install-whisper.sh --with-ffmpeg` (server `--convert`).

## 2026-10-22 · Infra: backups are a sidecar loop with snapshot-consistent row-count manifests
- **Decision:** The `backup` service uses the same `postgres:18.6-bookworm` image as the DB (matching `pg_dump`) and runs `infra/backup/pgdump.sh loop`. It sleeps in 5-minute chunks until 03:30 America/New_York, runs `pg_dump -Fc`, and keeps 30 days but never deletes the newest dump. If the last success is more than 26 h old at startup, it catches up. Each dump uses a snapshot exported from a REPEATABLE READ transaction, and the per-table exact row counts (`.counts`) are taken in that same snapshot. Cluster roles go in `.roles.sql`, without passwords. `restore.sh --drill` restores into a scratch DB and requires an exact row-count match. `--replace` takes a safety dump first.
- **Validated:** the dump, drill (pass and deliberate-mismatch fail), replace, and fresh-cluster replace (role and GRANT re-created) were run against a local Postgres 16 using macOS bash 3.2. The loop scheduling uses GNU `date -d`/`find -printf`/`stat -c`, which only exist in the container, so it is untested locally.

## 2026-10-22 · DB: keys, naming and column conventions
- **IDs:** uuid v7 generated app-side (`$defaultFn(newId)` in Drizzle). There is no DB default, so raw-SQL inserts must supply `id`. This works the same on PG16 (dev) and PG18 (prod).
- **Natural composite PKs** instead of a surrogate uuid, where the spec defines the identity: `balances(account_id, as_of)`, `targets(category_id, effective_from)`, `month_assignments(month, category_id)`, `budget_month_cache(engine_version, month, category_id)`, `budget_month_summary(engine_version, month)`, `loans(account_id)`, `settings(key)`. Every other table has a uuid `id`.
- **Names:** every money column ends in `_milli`, including the engine cache (`assigned_milli`, `activity_milli`, … rather than the spec's bare `assigned`/`activity`). TS properties are camelCase and SQL columns are snake_case (explicit names, no casing config).
- **Non-budget numbers:** AI `cost_usd` is `numeric(12,6)` (sub-cent precision; not household money). `confidence` is `real`. `holdings.quantity`/`price` and `loans.annual_rate` (a decimal fraction, 0.065 = 6.5%) are `numeric` and come back as strings.
- **Types from `pg`:** `client.ts` installs process-wide parsers (int8 → bigint, date → `YYYY-MM-DD`, int8[]/date[] arrays), so raw `pool.query`/`db.execute` results follow the same conventions as typed Drizzle reads.
- **drizzle-kit quirk:** it can't serialize bigint column defaults, so zero defaults are written as ``.default(sql`0`)``.

## 2026-10-22 · DB: additions and deviations from spec §5
- **Enums:** db enums reuse the `@homebase/shared` constants (account kind/source, category kind, cleared, flag, target type, cadence, frequency, catz method). `transaction_source` = account sources + `scheduled` + `reconciliation`. Db-only enums (roles, statuses, providers, purposes, …) are exported as `const` arrays from `schema.ts`.
- **transactions:** added `is_starting_balance` (§6.1: cash opening balance → `internal_rta`; card opening debt has category null, and **the engine must not treat it as uncategorized overspending**), `import_order` (YNAB order tie-break, §6.4), `ynab_id` (unique), and `scheduled_transaction_id`. Indexes: `(account_id, date)`, `(category_id, date)`, `date`, `payee_id`, `import_hash`, `transfer_pair_id`, a partial index on unapproved rows, and unique `(account_id, external_id)`. `transfer_pair_id` is a self-FK (`ON DELETE SET NULL`), so when bulk-inserting a pair, insert both rows first and then link them (the seed does this).
- **transaction_splits:** added `transfer_pair_id`, `sort` and `ynab_id`. The deferred constraint trigger (checked at commit) enforces Σ lines = parent amount for `is_split` parents, **and** that non-split parents have no lines. Soft-deleted parents are skipped. The same trigger exists for `scheduled_transaction_splits`.
- **YNAB mirroring:** `ynab_id` (unique) on accounts, category groups, categories, payees and scheduled transactions/splits. `deleted_at` soft delete on accounts, category groups, categories, payees and scheduled transactions, so deleted YNAB history still adds up (§6.9).
- **Other added columns:** `categories.always_review` (§9.4), `category_groups.is_system`; `targets.removed` (a tombstone row ends a target from that month on) and `targets.income_basis` (`rta_inflows` | `gross_pay`, §6.5); `categorization_events.shadow` (parallel-run shadow mode, §10) and `user_id`; `settings.enc_value bytea` for secret settings (VAPID private key, API keys); `connections.credentials_last4`; `asset_valuations.comps`; `scheduled_transactions.first_date`/`flag`; `reconciliations.statement_date`/`cleared_balance_milli`/`user_id`. Partial unique indexes allow one `cc_payment` category per card and exactly one `internal_rta` and one `uncategorized` category.
- **Auth tables:** `sessions` stores only the sha256 of the cookie token. `pin_attempts` has one row per attempt (user, IP, success) for the 5-in-15-minutes lockout and per-IP limits.
- **Engine cache:** `engine_version` is an `integer`. The views read `max(engine_version)`.

## 2026-10-22 · DB: reporting views and the read-only role
- **Views** live in the hand-written migration `0001_reporting.sql` (drizzle-kit can't see them). They are mirrored as `pgView(...).existing()` in `schema.ts` for typed reads. Changing a column that a view uses needs a new custom migration that drops and re-creates the view.
- **Two views beyond §5.5's six:** `v_month_summary` (RTA, assigned-in-future, Cost to Be Me and Age of Money for the latest engine version) and `v_balances_daily` (each account per day, carrying forward the last balance). `v_net_worth_daily` is built on it, and it answers per-account questions like "how much did Alex's 401k grow last month".
- **What the views include:** they expose names and amounts only. They never include `raw_description`, external ids or credentials, since their rows reach the LLM. `v_cashflow_monthly` covers on-budget accounts only. Income = inflows to RTA. Expense = everything else (net of refunds), including uncategorized spending and categorized transfers to tracking accounts. Pending rows and starting balances are excluded. `v_payee_spend_monthly` excludes transfers and income.
- **`homebase_ro`:** `src/migrate.ts` creates or updates it after every migration run. It gets LOGIN with `HOMEBASE_RO_PASSWORD`, or NOLOGIN when that's unset, and NOINHERIT. Settings: `statement_timeout=5s`, `default_transaction_read_only=on`, `idle_in_transaction_session_timeout=30s`. It gets SELECT on `public.v_*` only, and every other table privilege is revoked on each run. The views run with their owner's rights, so the role needs no base-table grants.

## 2026-10-22 · DB: secret encryption format
- **Format:** `encryptSecret` → `[key id: 1 byte][iv: 12][GCM tag: 16][ciphertext]`, with the key-id byte bound as AAD.
- **Rotation:** two new optional env vars. `HOMEBASE_MASTER_KEY_ID` (default 1) sets the id written into new ciphertexts. `HOMEBASE_PREVIOUS_MASTER_KEYS` (`id:base64,…`) lists retired keys that can still decrypt. `secretKeyId()` finds rows that still need re-encrypting.
- **Key requirement:** `HOMEBASE_MASTER_KEY` is required only when `NODE_ENV=production`.
- **`last4()`:** returns "" for secrets of 8 characters or fewer, so a short secret is never half-revealed.

## 2026-10-22 · DB: demo seed shape (`pnpm seed:demo`)
- **Determinism:** the seed is deterministic, ids included: a mulberry32 PRNG (seed 20261022) and uuid v7 with a fixed timestamp base, with "today" = 2026-10-22, covering May 2025 to Oct 2026.
- **Safety:** it truncates every table in one transaction. It refuses (unless `--force`) when the DB holds transactions but no `settings.demo_seed` marker, so it can't wipe real data by accident.
- **Budgeting pattern:** Alex is paid monthly on the 25th (or the prior business day), net $7,930 in 2025 and $8,305 in 2026 (every figure in the seed is made up). Each paycheck is assigned the *following* month, so each past month ends with RTA ≈ that month's paycheck. Overspending is covered in the month it happens, and the remainder (which can be negative) goes to 💰 Savings.
- **October 2026:** RTA of $412.18 is left unassigned, and $290 is assigned ahead into Nov 2026. Misc is −$137.42 and Eating Out is −$64.18, both credit overspending (card-only). Uncategorized activity is −$426.50 (three Amazon charges with AI suggestions). There are 11 unapproved transactions in the last 10 days and one pending gas swipe on the 22nd. The Giving target has history: $450 from May 2025, $500 from Jan 2026.

## 2026-10-22 · Engine: [VERIFY] choices in the budget engine (§6)
Sources: YNAB support articles (fetched Oct 2026: credit cards overview, credit card overspending, refunds and returns, positive balance, paid-in-full cards, red/underfunded payment category, month rollover, negative RTA, overspending, targets, underfunded, auto-assign, age of money) and the YNAB OpenAPI spec. Every choice below is a `BudgetOptions` / `AutoAssignOptions` switch, so the §6.9 golden run can flip it (`HOMEBASE_GOLDEN_OPTIONS='{"…":"…"}'`) without code changes.

- **E1 Mixed cash and credit overspending** (`overspendAttribution`). **Verified by the golden run (2026-10-23) → default `cash_first`.** Funds(c) for credit = carry + the month's full assigned + every inflow to c in the month (refunds included, retroactively); cash outflows take from it first; then card outflows are funded in (date, importOrder, id) order. Whatever Available is left negative is credit overspending up to the unfunded card spending; the rest is cash overspending (red when both). This matches YNAB's "takes the cash out first". The spec's original single chronological pass (`chronological`) produced card-payment and RTA mismatches from the first mixed month on and stays only as an option.
- **E2 Card starting balance** (`cardStartingDebt`). The default is `no_budget_effect`: a negative `isStartingBalance` transaction on a credit account touches no category and not RTA, whatever its category. It only adds to the card's debt, so P(K) is Underfunded by that debt. This matches YNAB's paid-in-full article ("yellow alert … prompting you to plan for your Starting Balance"). A positive starting balance with no category, on any account, goes to Ready to Assign.
- **E3 Negative RTA carries forward** (`negativeRtaCarries: true`). RTA is cumulative. YNAB's rollover and negative-RTA articles say overspending is "removed from the leftover Ready to Assign" and that "Ready to Assign becomes negative after a month rolls over".
- **E4 Negative payment-category balance = cash overspending** (`paymentCategoryNegative: "cash_overspend"`). YNAB: "Red Available amounts indicate cash overspending. Red in your Credit Card Payment category means you made a payment for more than you had Available." At rollover it resets to 0 and is subtracted from next month's RTA. `carry` is the alternative.
- **E5 A refund larger than the funded portion** subtracts the full refund from P(K), which can then go red (= E4). Under E1, a refund in the same month counts toward Funds(c), so it retroactively funds that month's card spending in c. A refund only turns P(K) red when it arrives after the funded money has left, e.g. in a later month after the card was paid. YNAB's refunds article: the refund "will move money from the Credit Card Payment category", and the payment category can "go red and negative".
- **E6 Credit cards with a positive balance** (`cardPositiveBalanceToRta: "rta"`):
  - A payment reduces P(K) by the full amount. The part of any non-RTA inflow (payment or refund) that pushes the card balance above zero is added to RTA as "Inflow from Debt Account". YNAB: an overpayment turns the payment category red and the positive balance "has been added to Ready to Assign".
  - Spending from a positive balance acts like cash: no money moves to P(K), and unfunded spending is cash overspending. A purchase that crosses zero moves only the part that creates debt.
  - A transfer out of a positive card has no budget effect. A cash advance (card → on-budget cash account) adds the new debt to P(K).
  - Card-to-card transfers move nothing between payment categories ("Money will not move between Credit Card Payment categories automatically").
- **E7 Ready to Assign: raw vs displayed** (`rtaDisplay`). **Verified:** YNAB's month `to_be_budgeted` is the raw cumulative figure `rta(M)`: carry + income + debt-account inflow − last month's cash overspending − assigned. No future-month adjustment; the future-adjusted variant was off in a month where later months were assigned. So the golden test compares `MonthResult.rta`. `readyToAssignDisplay` keeps `future_min` for the Plan banner (YNAB: "RTA is current in the future-most month"; assigned-in-future is the difference). That UI behavior is from the docs and still unverified against the live UI.
- **E8 Targets.** Multi-month and by-date needs are rounded *up* to whole cents. `percent_of_income` is rounded half-up to whole cents. `balance` (TB) ignores this month's activity, per the spec (`balanceTargetIncludesActivity` to flip). When a category has both a target and upcoming scheduled transactions, needed = max(target need, scheduled need), where scheduled need = max(upcoming − (carry + activity), 0). A payment category with no target needs max(debt − (carry + activity), 0). Snoozed targets need 0, but Reduce Overfunding still uses the unsnoozed need (per YNAB). YNAB `goal_cadence` codes were checked against the OpenAPI spec: 0/1/2/13 repeat every `goal_cadence_frequency` units; 3–12 = every 2–11 months; 14 = every 2 years. Imported snooze month is the America/New_York month of `goal_snoozed_at`.
- **E9 Age of Money.** Only on-budget cash accounts are considered.
  - Starting balances are buckets (`ageOfMoneyStartingBalances`) but never outflows.
  - Card payments are outflows. Transfers between cash accounts are excluded. Card spending and card inflows are not counted until the card is paid.
  - Each outflow's age is the amount-weighted age of the FIFO buckets it used. Money with no bucket (overdraft) is 0 days old.
  - AoM is the mean over the last 10 outflows, **rounded half up**, null with fewer than 10. Against YNAB's monthly figures, rounding matches about two-thirds of the months, flooring almost none. Not counting starting balances as buckets is far worse, so they stay buckets.
  - Remaining gaps are within a few days, except one month that is about a month off. Still not asserted in the golden test, which prints both values. **[VERIFY]** open.
- **E10 Auto-Assign "Underfunded"** (`order`). The default `spec` funds targets in sort order, then upcoming scheduled transactions, then overspending, then payment categories. `ynab` follows YNAB's documented order: overspending; scheduled and dated targets by date; end-of-month targets; future-dated targets; then card payments. It skips "have a balance" targets with no date. In both orders, payment categories are re-evaluated after an engine re-run, so credit overspending that was covered isn't funded twice. With no selection, funding stops when RTA runs out. With a selection, the selected categories are fully funded even if RTA goes negative (YNAB's warning), unless `capToRta` is set.
- **E11 YNAB import mapping.**
  - Payment categories (group "Credit Card Payments", category not `internal`) are linked to on-budget liability accounts by exact name. Unmatched ones are imported as normal categories, with a warning.
  - YNAB's built-in, unassignable "Credit Card Interest" category is a normal hidden category. Its card charges become credit overspending, so P(K) shows underfunded, as YNAB documents.
  - Starting balances are detected by the payee "Starting Balance".
  - `importOrder` is the position in the export array.
  - Schedule "twiceAMonth" falls on the anchor day and the day 15 days away (clamped to month end).
  - The engine does not use zod, because its only dependency is @homebase/shared. The mapper validates by hand and reports the JSON path on errors.

## 2026-10-22 · Connectors: read-only enforcement (§4.6)
- **Decision:** All network I/O in `packages/connectors` goes through `src/http.ts`. It throws `read_only_violation` for any method other than GET. The only exception is a body-less POST that passes `allowWrite: "simplefin.claim"`; `WRITE_ALLOWLIST` is a frozen one-element array. The claim POST is never retried. `test/readOnly.test.ts` statically scans every file in `src/` for: `fetch(` outside http.ts; alternate HTTP stacks (`node:http(s)`, undici, axios…); non-GET `method:` literals (POST allowed only inside `claimSetupToken` in simplefin.ts); write-verb literals; `allowWrite` outside simplefin.ts; and `child_process` outside gusto.ts. A meta-test proves the scanner catches violations. At runtime the test drives every network connector through a recording fetch and asserts exactly one non-GET call (the claim).
- **Gusto:** the CLI wrapper builds argv as an array and runs it via `execFile` (no shell). Only `api request --method GET <path> --json` is allowed, for an allowlist of `/v1/companies/{uuid}[/payrolls[/{uuid}]|/pay_schedules|/employees]` and `/v1/me`, with allowlisted query keys. **[VERIFY]** the exact `gusto api request` flag spelling against `gusto api request --help`; the README doesn't document it.

## 2026-10-22 · Connectors: SimpleFIN specifics
- **Windows:** default 45 days, not 90. The live Bridge returns `gen.api` "exceeds recommended range of 45 days". `dateWindows()` accepts up to 90. Window bounds are local (America/New_York) midnights in epoch seconds; `end-date` is exclusive.
- **Credentials:** `fetch()` rejects URLs with embedded `user:pass@`, so the Access URL is split into a clean base URL plus an `Authorization: Basic` header. Errors redact userinfo, Basic/Bearer values and registered secrets.
- **Liability sign:** the protocol says a positive balance means amount owed, but the live card data (fixture, 2026-10) already reports cards as negative. So `auto` negates a **positive** card/LOC balance and keeps ≤ 0 as-is. Mortgages and loans are always −|balance|. The per-account overrides are `positive_is_debt` and `negative_is_debt`. Known edge case: an overpaid card that reports positive credit under the negative convention is misread in `auto`, and needs the override.
- **Holdings cost basis:** normalized to a **position total** (`ExternalHolding.costBasis`). Fidelity, Vanguard, Schwab and E*Trade send totals and are kept as-is. For other institutions the protocol says the value is per share, so it is multiplied by shares, unless a bigint ratio check against `market_value` shows the per-share reading is ≥ 3× off and the total reading is closer. Holdings parsing never throws: bad lots become warnings and the account degrades to balance-only.
- **errlist:** `con.auth`/`gen.auth` → `needs_attention` (banner "Reconnect <org_name> in SimpleFIN"); `act.*`/other `con.*` → `retry_later`; `gen.*` → info. HTTP 402 → `subscription_lapsed`, 403 → `revoked`, claim 403 → `already_claimed`. v1 `errors[]` strings become `gen.legacy` items, and v1 per-account `org` objects are turned into `connections`.
- **Budget:** `checkSimplefinBudget(usage, kind, cost)` is pure: at most 6 requests/day total and 2 manual/day. A multi-window backfill costs one request per window.

## 2026-10-22 · Connectors: normalized shapes and dates
- `ExternalTxn.date` is the local America/New_York date of transacted-at if known, else posted (§6.1). This applies to every source: SimpleFIN `transacted_at`; Mercury `createdAt` (Mercury's `start`/`end` filters also use createdAt); Coinbase `created_at`; River `Date (UTC)`; OFX `DTUSER` before `DTPOSTED`. An OFX time is converted from GMT only when it carries a real GMT time; non-GMT offsets and midnight/noon pads keep the written calendar date.
- Quantities (shares, BTC) are canonical decimal **strings**; BTC math uses satoshi bigints. Money is bigint milli everywhere. Mercury, RentCast and Coinbase send JSON numbers, which go through `dollarsToMilli` (toFixed(4) then exact parsing).
- Privacy: account numbers never leave the importers. Fidelity and OFX account ids are `sha256` prefixes plus last-4. Mercury `accountNumber`/`routingNumber` and the Fidelity "Account Number" column are stripped from `raw`.
- Coinbase is modeled as one tracking account (`externalId: "coinbase"`, USD balance = Σ `native_balance`), with one holding per non-zero wallet. Transactions carry `asset: {symbol, quantity}`, and `amount` is the USD native amount. River works the same way (amount = USD value of the BTC movement).
- Mercury statuses: pending → pending; sent → posted; failed/cancelled/blocked/**reversed** → skipped. `reversed` isn't in spec §7.2; it's skipped on the assumption that Mercury shows the reversal as its own row. **[VERIFY]**
- River BTC delta per row = received(BTC) − sent(BTC) − fee(BTC). This assumes River's "Sent Amount" excludes the fee. **[VERIFY]** against a real export (the River help article returned 403 to our fetcher).

## 2026-10-22 · Connectors: amortization rounding
- **Decision:** Rates are exact decimal strings in percent ("6.5"). `fractionToPercent("0.065")` converts the DB's `loans.annual_rate`. Every computation is a bigint rational. The level payment is rounded half away from zero to cents. Each period's interest is rounded to cents. The **final scheduled payment (maturity) absorbs the rounding remainder**, so 300k@6.5%/30y is 359 × $1,896.20 + one $1,900.91 payment. That gives $382,636.71 total interest vs the textbook $382,633.47 with an unrounded payment. The closed-form `balanceAfterPayments` agrees with the iterative schedule to within a few cents.
- **loan_events:** an event dated d applies after the last payment due on or before d, so it's in effect before the next period's interest accrues. `recast` and `rate_change` re-amortize the current balance over the remaining term (maturity unchanged) unless the servicer's `newPayment` is given. `balance_correction` snaps the principal. Escrow is out of scope (P&I only). Drift is flagged when |synced| − |scheduled| exceeds $50.

## 2026-10-22 · AI: usage accounting and the monthly cap

## 2026-10-22 · AI: Ask agent loop (§11.2–11.3)
- **Manual streaming loop:** `runAgent()` is an async generator that yields `text_delta | tool_call | tool_result | chart | pending_action | error | done`, and `toSseFrame()` serializes events for SSE. The loop allows 12 tool iterations. After the 12th, one final request with `tool_choice: {type: "none"}` makes the model answer with what it has (`stopReason: "iteration_cap"`). Any `tool_use` that isn't run (cap, `max_tokens`) gets an `is_error` tool_result appended, so the persisted history stays valid.
- Caching: the tool list is deterministic with a breakpoint on the last tool. `system[0]` (rules, memory, category tree, accounts) has a breakpoint. `system[1]` holds the volatile date/time and speaker. Top-level automatic caching covers the growing conversation. That is 3 of the 4 allowed breakpoints. Chat runs Sonnet at effort `medium`; deep mode runs Opus at `high`.
- Tools use `eager_input_streaming: true`, and **every input is validated with Zod** before use. A stream that fails on unparseable tool JSON is re-issued at most twice; API errors are surfaced, never retried in the loop.
- **Write tools never execute in the loop.** They validate, build a human diff ("Move 14 transactions ($612.40) from Misc → House Projects") from context lookups, and save a `PendingAction`. The model is told the change hasn't happened yet. `executeConfirmedAction()` re-validates the input, does a compare-and-set `awaiting_confirmation → executing` (so a confirmation applies to that card only and runs at most once), runs the injected executor, writes `audit_log` (`actor: "ai"`, `confirmedBy: <user>`, `userId: <requester>`), then marks the card `confirmed` (or `failed`, with no audit row).
- Amounts the model sends to write tools are **dollar strings** (`"612.40"`) and are converted with `parseMilli`, so floats never touch money. Read-tool results are serialized with bigint → `"-$612.40"` and redacted.
- `speech`: the model ends each reply with `<speech>…</speech>`. A streaming extractor hides the tag from the text deltas, even when it is split across chunks. If the tag is missing, the speech is derived from the markdown (first two sentences, formatting stripped).
- `create_rule` takes a simplified, model-friendly input (payee_equals/contains, description_contains, abs amount range, accounts → category, rename, auto_approve). The web app's executor maps it to the categorizer rule format, because `ai` can't import `categorizer` (categorizer depends on ai).

## 2026-10-22 · AI: SQL tool guard (§4.6)
- `validateSelectSql` is a lexical scanner: strings and quoted identifiers are blanked, comments stripped, and dollar-quoting and `$n` parameters rejected. It enforces a single statement (an optional trailing `;`) starting with SELECT/WITH. It rejects DML/DDL/utility keywords (including `INTO`, `RETURNING`, `SET`), locking clauses, `pg_*`, `dblink*`, `lo_*`, `set_config`, `current_setting`, `*_to_xml`, `txid_*`, sequence functions, `information_schema` and `pg_catalog`. FROM/JOIN targets must be §5.5 views, CTE names, or a short list of set-returning functions; FROMs inside `EXTRACT(… FROM …)`, `SUBSTRING(… FROM …)` and `IS DISTINCT FROM` are skipped. The query is wrapped as `SELECT * FROM (<sql>) q LIMIT 501`, and the result is truncated to 500 rows with `truncated: true`.
- This guard is the first layer only. The real boundary is the injected `ReadOnlySqlExecutor`, which must use the `homebase_ro` role (SELECT on the views only) and run `readOnlySqlStatements()`: `BEGIN TRANSACTION READ ONLY`, `SET LOCAL statement_timeout = '5000ms'`, the query, then `ROLLBACK`.

## 2026-10-22 · Categorizer: rules format and semantics (§5.2)
- `rules.conditions` is a JSON array, ANDed. Each entry is one of: `{field: payee|raw_description, op: equals|contains|regex, value}`; `{field: amount, op: equals, valueMilli, sign}`; `{field: amount, op: range, minMilli?, maxMilli?, sign}`; `{field: account, op: in, accountIds}`; `{field: day_of_month, op: range, from, to}`. A range with `from > to` wraps around month end. Amounts compare on **absolute value**, with `sign: outflow|inflow|any`. Milliunits are stored as decimal strings. `payee equals` compares normalized keys. Regexes are case-insensitive, capped at 200 chars, and an invalid pattern never matches.
- `rules.actions` is `{setPayee?, setCategoryId?, setMemo?, split?, transferAccountId?, autoApprove?}`. Split templates are `percent` (stored as "33.33" and held as basis points that must total 100%) or `fixed` (with at most one `remainder` line; otherwise the last line takes the remainder). Allocation is largest-remainder, in cents when the amount is whole cents and in milliunits otherwise, so lines always sum exactly.
- Order: enabled user rules, then learned rules, each by priority then id. `ai_suggested` rules are proposals and are never applied. Each action field comes from the first matching rule that sets it, so a rename rule can combine with a later category rule. The first rule that supplies a category, split or transfer is the deciding rule, and its hit is recorded.
- An explicit rule `autoApprove: true` overrides the "always review" category flag, but **not** the first-3-reviews rule for income above $500 or Ready to Assign.

## 2026-10-22 · Categorizer: history, transfers, approval
- History confidence is 0.90 at 3 transactions, plus 0.01 per extra one, capped at 0.98. It is reduced by (1 − share) × 0.2, with a floor of 0.90. So auto-approve at ≥0.95 needs about 8 consistent transactions. Amount bands are tried only when no category reaches 90%. A band needs two sides, each with ≥3 transactions, ≥90% purity and different categories; the threshold is the whole-dollar midpoint of the gap (Costco: $60). A payee's `default_category_id` is used as history at 0.95 when history isn't decisive.
- Transfers are auto-applied for: card payments (household checking/savings/cash → card/LOC); business → household on-budget (Mercury → household checking), where the household side gets Ready to Assign; and **household on-budget ↔ on-budget moves only when both descriptions look like transfers** (an extension beyond §8.3's explicit list, judged unambiguous). Everything else is a suggestion: tracking accounts, household → business, a weak description on one side, or more than one candidate on either side. A counterpart account is "mentioned" when its full name, nickname or institution appears, or all of its distinctive words do.
- §9.4 is implemented as specified. AI auto-approve requires |amount| strictly below $150. The default "always review" set is Misc, the uncategorized kind, and any category or group named Savings. Settings can pass an explicit list instead.

## 2026-10-22 · Categorizer: recurring, anomalies, evaluation
- Recurring series are found per payee and direction. Amounts are first split into clusters at gaps >1.5× (so two Apple subscriptions stay separate, while a variable utility bill stays one series). Cadences are weekly 7±3 days (≥4 occurrences), monthly 28–31±3 (≥3), and yearly 365–366±3 (≥2). At least 75% of intervals and the latest interval must match. "Stable" means ≥60% of consecutive amounts are equal within 1%. A price change is reported only from a stable series whose previous plateau had ≥2 charges.
- Anomaly statistics use cents as JS numbers. This is descriptive math for a flag, not ledger arithmetic; reported amounts are bigint. A payee baseline needs ≥5 samples, otherwise the category baseline is used. When σ = 0, a transaction is flagged if it is >2× the mean and ≥$10 more. Amounts under $25 are ignored.
- **Evaluation harness (no leakage):** training is every labeled transaction dated before `windowStart`. Held-out bank rows are visible **without labels**, as they would be at sync time, so transfer pairs can match. Supplied payee records have `defaultCategoryId` stripped. Rules created after the window must not be passed in. Similar-transaction lookups are limited to dates before each transaction. Splits are excluded from scoring. A transfer label is correct when the prediction is a transfer.

  - `confirmed` = `confirmed` + `confirmed_at` set
  - `failed` = `confirmed` + `error` set

  `transition()` is a conditional `UPDATE … WHERE <from-state predicate> RETURNING`, which is a true compare-and-set: two concurrent Confirms run the executor once. `requestedBy` comes from `ai_conversations.user_id`. `conversation_id` is required.
- **`DbAgentRecorder`:** writes `ai_messages` (a user string is stored as a text block, along with model, tokens and cost) and `ai_tool_calls` rows for read tools (status `auto`; failed calls also set `error`). Write-tool rows come from the store returned by `recorder.pendingActionStore()`, which links them to the assistant message. `createConversation` and `loadConversationHistory` are helpers.
- **`DbAuditSink`:** writes `audit_log`. Bigint values in before/after are stored as strings.
- **`DbReadOnlySqlExecutor`:** opens its own pool as `homebase_ro`. The URL comes from `HOMEBASE_RO_DATABASE_URL`, or from `DATABASE_URL` with user/password swapped for `homebase_ro` / `HOMEBASE_RO_PASSWORD`. On first use it checks `current_user`, then runs each query as BEGIN READ ONLY, `SET LOCAL statement_timeout`, the query, ROLLBACK. `runGuardedSql` now returns int8 values as plain strings, so a `count(*)` is never formatted as dollars.
- **Integration tests** run against per-package databases next to `TEST_DATABASE_URL` (`homebase_categorizer_test`, `homebase_ai_test`), migrated and demo-seeded on every run. They don't reset `homebase_test`, which the db package's suite drops and recreates. They skip when Postgres isn't reachable.

## 2026-10-22 · Core: service shape
- **Decision:** `@homebase/core` services take a Drizzle `db` (pool or open transaction) for reads and a `Ctx { db, userId, actor: user|ai|system, confirmedBy?, today? }` for writes. Each write is one transaction (a savepoint when `ctx.db` is already a transaction) that writes `audit_log`. `actor: "ai"` without `confirmedBy` throws, so the "no AI writes without confirmation" rule is enforced in core and not only in the UI. `today` is injectable (America/New_York), so tests and jobs pin the date.
- **Errors:** `NotFoundError`, `ValidationError` and `ConflictError` (stale undo, row in use, name clash) carry a `code` that callers map to responses.
- **Queries on a transaction run one at a time** (`inOrder`). `Promise.all` over a single pg client pipelines queries, which pg deprecates.

## 2026-10-22 · Core: engine cache freshness and recompute
- **Freshness:** `settings[engine_cache_state]` stores `{engineVersion, fingerprint, asOf, through, firstMonth, dirtyFrom}`. The fingerprint is `current_database()` plus `count(*)` and `max(updated_at)` for each engine input table (accounts, groups, categories, transactions, splits, assignments, targets, scheduled and their splits, payroll_runs). A read (`ensureFresh` / `getBudgetMonth`) recomputes when the engine version, the fingerprint, `today` or the month range differ.
- **Writes through core** call `beginBudgetWrite` (advisory lock, and a note of whether the cache was current before the write), then `finish(earliestAffectedMonth)`, which recomputes inside the same transaction. If the cache was already stale, `finish` does a full rewrite, so it never marks stale months as fresh.
- **Writers outside core** (sync worker, YNAB import) either call `invalidateBudget(db, month)` or do nothing. If they do nothing, the fingerprint changes and the next read does a full recompute (about 35 ms on the demo data).
- **What gets rewritten:** `budget_month_cache` rows are rewritten from the earliest affected month on. `budget_month_summary` rows are all rewritten every time, because the displayed RTA and assigned-in-future for month M depend on every later month (E7). When an assign-ahead extends the range, the gap months are filled too. Recompute runs READ COMMITTED with the advisory lock as its first statement (a REPEATABLE READ snapshot would predate the lock wait and collide with the previous holder's rows). The read path (`ensureFresh`) re-checks freshness once it holds the lock, so concurrent callers queue, one rewrites and the rest skip. The fingerprint is taken *before* loading, so a concurrent commit can only make the cache look stale, never look fresh when it isn't.
- **`budget_month_summary.rta_milli` is the displayed RTA** (`readyToAssignDisplay`), so `v_month_summary` / the AI see the number the Plan screen shows. Raw RTA = `rta_milli + assigned_future_milli`.
- **Engine detail the cache schema lacks** (status label, cash/credit spending, target progress, payment detail) comes from the last `BudgetResult`, kept in a per-process memo keyed by the fingerprint. On a cold process the engine reruns in memory without writing. Months outside the cached range are computed on the fly (`fromCache: false`).
- **Plan summary panel:** "left over / assigned / activity / available" are sums over every non-RTA category (hidden and deleted included), so leftover + assigned + activity = available. The engine's RTA carry-in is exposed separately as `rtaLeftOverFromLastMonth`.

## 2026-10-22 · Core: undo/redo format
- **Payloads:** `budget_operations.payload` / `inverse` are `{v: 1, action, args, changes?, rows?}`.
  - `changes` are engine `AssignmentChange`s, with money as decimal strings.
  - `rows` are generic `RowChange`s for `targets`, `month_notes`, `categories` and `category_groups`. Before and after are stored as row JSON with numbers stringified, and restored with `jsonb_populate_record`, so no per-table undo code is needed.
- **Undo and redo** apply the stored side only if every cell or row still equals the expected value. Otherwise they throw `ConflictError`, and nothing is half-applied.
- **Not undoable:** the seeded demo operations (legacy shape, listed in Recent Moves with `canUndo: false`) and `mergeCategories` (`args` only, `inverse: {}`).
- **Targets:**
  - `editTarget` writes an `effective_from = month` row (default: the current month) and drops rows effective after it, so the edit applies "from here on".
  - `snoozeTarget` copies the effective target into the snoozed month rather than setting `snoozed_month` on an older row, so earlier months never change.
  - Removing a target writes a `removed` tombstone.

## 2026-10-22 · Core: smaller choices
- **Accounts:**
  - The household entity is the one with the lowest `sort`. Every other entity counts as the business: off budget by default, excluded from net worth, holdings, spending and wealth sections unless `includeBusiness`.
  - Creating (or switching on budget) a credit card or line of credit creates or undeletes its `cc_payment` category in the system "Credit Card Payments" group. Renaming the card renames the category if it still has the card's old name.
  - A starting balance creates an `is_starting_balance` transaction: cash goes to Ready to Assign, card debt gets no category (E2). It also creates a `balances` row.
- **Account balances:** `listAccounts().balance` is the working balance for on-budget accounts. For tracking accounts it is the latest `balances` snapshot, because their ledger holds only transfers (contributions, mortgage payments). It falls back to the working balance when there is no snapshot. So Σ household balances = net-worth headline.
- **Raw-SQL timestamps:** drizzle's node-postgres driver returns timestamp/timestamptz as text from `db.execute`. Core converts every raw timestamp with `toDateOrNull`/`toDate` (`src/json.ts`), so callers always get `Date`.
- **Account status color:** taken from `connections.status` when the account has a connection. Otherwise, synced sources are green when the latest balance snapshot is no more than 2 days old, else yellow, and manual / amortization / YNAB accounts are gray.
- **Reconcile:** the adjustment payee is "Reconciliation Balance Adjustment" (source `reconciliation`). The category is RTA for cash, the card's payment category for cards (§6.2), and none for tracking accounts. It then marks every `cleared` row `reconciled` and writes `reconciliations` with the pre-adjustment cleared balance.
- **Scheduled transactions:** `materializeDue(today)` is idempotent per (schedule, date, account). It creates uncleared, unapproved rows (pairs for transfers) and steps `next_date` with the engine's `occurrences()`, anchored on `next_date`. The demo seed's `first_date` days don't match `next_date` (e.g. payroll `first_date` 2025-05-01, `next_date` 2026-10-23), so `first_date` isn't a usable anchor. Schedules that end are soft-deleted.
- **Payees:** merging re-points transactions, splits, schedules and aliases. It adds an exact alias for the source name and frees the source's `normalized_key` (it becomes `merged <id>`) before soft-deleting it.
- **Investment growth:** known contributions = transfers into the account that month, plus `accounts.monthly_contribution_milli` for completed months. Gusto payroll deductions aren't mapped to accounts yet. That needs a deduction-key → account setting (Phase 8). With neither source, the month is labelled "market change + unknown contributions".
- **Holdings:** quantities are summed in Postgres `numeric` and returned as strings. Asset class is a name/symbol heuristic.
- **Test database:** core's suite uses `<TEST_DATABASE_URL name>_core_test` (default `homebase_core_test`, created if missing; `CORE_TEST_DATABASE_URL` overrides it). That way it never races the db package or other packages resetting `homebase_test` in parallel. Like the db suite, it refuses any database whose name doesn't end in `_test`. Migrations run once per run (`globalSetup`), and each test file re-seeds the demo data.

## 2026-10-22 · Worker: sync bookkeeping and the SimpleFIN budget
- **`sync_runs.errors` is an object**, not a list: `{trigger: scheduled|manual|cli, issues[], warnings[], error?, skipped?}`. The trigger is what lets the budget tell manual requests from scheduled ones. `requests_used` is incremented *before* each HTTP request, so a crash still counts.
- **SimpleFIN budget** is per connection (one Access URL = one quota) and counts `sum(requests_used)` since local midnight: ≤ 6/day total, manual ≤ 2/day (`checkSimplefinBudget`). The HTTP client runs with `retries: 0` for SimpleFIN so every attempt is one counted request; pg-boss retries re-check the budget. A run that doesn't fit is skipped (no sync_run row, no retry).
- **Windows:** normal runs fetch `[today−14, today]` with `pending=1`. Backfill target = `sync_start_date − 30` (`settings.sync_start_date`, set on the first SimpleFIN/Mercury sync). On the first run, if one 45-day window covers target..today it is a single request; otherwise windows are planned newest-first (normal window, then backfill from newest to oldest) and the largest prefix that fits today's budget runs. Progress is `connections.meta.backfill {target, coveredFrom, done}`.
- **raw_payloads:** one row per request (SimpleFIN set incl. window, Mercury/Coinbase raw arrays, RentCast AVM, YNAB delta). Purged after 14 days at the end of SimpleFIN/Mercury syncs. Bodies never contain credentials.
- **Connection health:** `connections.meta.needsAttentionSince` (kept at its first value) and `meta.issues` (SimpleFIN errlist with banners). `health.connections` pushes admins when needs_attention has lasted ≥ 24 h. `markConnectionOk` clears both.

## 2026-10-22 · Worker: ingest rules (§8.2, §8.4)
- **New accounts inbox:** `accounts` has no meta column, so the inbox is `connections.meta.inbox [{accountId, externalId, name, kindGuess, detectedAt}]`. New accounts are created off budget (Household; Mercury → the business entity) with the guessed kind. `connections.meta.accountMap[externalId]` either links an existing account (`{accountId}`: sets its connection/external id and switches `source` to the provider; used to attach YNAB-imported accounts before the parallel run) or gives explicit creation settings (`{name, kind, onBudget, entity}`), which bypass the inbox. Settings owns both lists.
- **Matching order for a posted row** with an unknown external id: (1) YNAB-imported row (source `ynab_import`, no external id; exact amount, ±3 days, fuzzy payee; YNAB transfer rows also match bank payment/transfer descriptors) → linked in place, `matched_ynab_id = ynab_id`, source becomes the provider, YNAB category/memo/splits/cleared kept; a pending copy of the same purchase is soft-deleted. (2) pending row (±20% same sign, ≤ 7 days, similar payee) → replaced in place (id, category, memo, payee, splits, flag kept; `approved` reset when the amount moved; split lines rebalanced on the largest line). (3) materialized scheduled row (±$1, ±4 days; pending rows too) → replaced in place. (4) insert (unapproved, uncategorized). Known external ids only refresh bank fields; reconciled and user-deleted rows are left alone.
- **Fuzzy payee** = a shared significant token (≥ 3 chars, not digits, not store/state/card noise) or a prefix, else bigram Dice ≥ 0.35. A YNAB row with no payee text matches only when it is the sole candidate.
- **Vanished pending rows** inside the fetched 14-day window are soft-deleted (released holds), except for accounts/institutions that reported errors this run.
- **Transfers** use `@homebase/categorizer`'s `detectTransferPairs` over unpaired, uncategorized, non-pending rows from 5 days before the earliest touched row. Auto pairs are linked both ways with `catz.method = transfer`; a business draw into a household account gets Ready to Assign. Suggestions are returned in the ingest result but not persisted yet (no review-queue table).
- **After ingest:** `categorize.pending` is enqueued with the touched ids, and `@homebase/core`'s `recompute` runs from the earliest touched month. Ingest writes do not call `invalidateBudget`; core's fingerprint catches anything else.

## 2026-10-22 · Reports (§13): core module, rules and URL shape
- **Where:** `packages/core/src/reports/` (exported through `export * from "./reports/index"`; the older `src/reports.ts` with `spendingSummary` and saved-report CRUD stays). Every report is `xxxReport(db, params)` over the common `ReportParams` (`period` month|quarter|ytd|last12|custom, `month` anchor, `from`/`to`, `accountIds`, `entity` household|business|all, `level` category|group, plus `categoryId` for category detail and `accountId` for investment growth). `runReport(db, slug, params)` dispatches by slug; `REPORTS` holds titles, blurbs and each report's default period/level. - **Which lines count** (`reportScope`, SQL over `v_transactions_flat`): household = on-budget accounts of the household entity; income = inflows categorized to Ready to Assign; spending = every other line net of refunds except uncategorized transfers (on-budget transfers, card payments). Categorized transfers to tracking accounts (retirement contributions, the mortgage) are spending, as in YNAB and `v_cashflow_monthly`. Pending rows and starting balances never count. **Business** accounts are tracking accounts with no categories, so there income = non-transfer inflows and spending = non-transfer outflows, bucketed by payee (`payee:<id>` keys) and grouped under the entity. `entity: all` is the union.

Budget performance leaves out the in-progress month when the period spans more than one month. "Overspent" = month ended with Available < 0; because overspending is normally covered in-month, the report also shows **over plan** = months where spending exceeded that month's assignment, with the average excess. Suggested assignment = average monthly spending rounded **up** to whole dollars.
- **Category detail** defaults to the category (or group) with the most spending in the period. "Met target" = a target in effect with need > 0 and nothing underfunded (group level: every targeted category met).
- **Subscriptions** run `detectRecurring` over the full history up to the period's end (so yearly charges show in a month view), keep `isSubscription` series, annualize the latest charge (×52/×12/×1) and call a series active while `nextExpectedDate + grace` (7/10/30 days) ≥ period end. Price increases and new subscriptions are relative to the period start. Recurring bills (mortgage transfer, giving, insurance) qualify too; nothing filters them out.
- **Cash flow sankey:** sources (income payees, top 5 + "Other income") → one hub node "Income" → groups → categories (top 6 per group + "Other …"). Only positive buckets flow; the hub balances with a "Kept" sink or a "From earlier months" source. Node names are made unique with suffixes because ECharts keys nodes by name. Phones show sources → groups only.
- **Net worth** samples month ends (the last capped at `to`) for long periods, weeks up to 120 days, days up to 45; the start point is the day before the period. **Investment growth** reuses core `investmentGrowth` per account and sums.
- **Saved reports:** `saved_reports.spec` may be an Ask `ChartSpec` (rendered as stored), a reference `{report: slug, params}` (params without defaults; opening it redirects to the live report), or the demo seed's provisional `{source: "v_transactions_flat", x, filters}` shape (run live as a household spending query and returned as a ChartSpec). Core now depends on `@homebase/ai` (ChartSpecSchema) and `@homebase/categorizer` (recurring detection); neither depends on core.
- **Drill-down:** `drillDown(report, target | "category:<id>|month:YYYY-MM-01", params)` returns `TransactionFilters` for `listTransactions` and an `/activity?category=&payee=&from=&to=&account=` link. Group rows pass `category` as a **comma-separated** list of the group's category ids; uncategorized rows pass the system Uncategorized category id.
- **URLs:** `/reports/<slug>?period=&m=YYYY-MM&from=&to=&entity=&level=&accounts=a,b&category=&account=`; parameters equal to the report's defaults are omitted (`paramsToSearch(p, reportDefaults(slug))`, mirrored client-side in `components/reports/url.ts`). CSV: `/reports/<slug>/export?<same>` (RFC 4180, CRLF, decimal dollars, percent with two decimals); saved charts: `/reports/saved/<id>/export`. PNG is client-side: the chart's SVG is cloned with computed colors inlined (CSS variables don't survive serialization) and drawn on a 2× canvas under the title. Ranked bar lists are plain SVG (`RankBars`) so they export too.

The Reports index warms the cache once before running its reports in parallel; the underlying race is in `budget/cache.ts`.

## 2026-10-22 · Security review fixes
- **Context:** a review found five issues. (1) Critical: with `TS_USERSPACE=true`, tailscaled's netstack forwards inbound tailnet TCP on any port to `127.0.0.1:<port>`, skipping Serve. Any tailnet peer could `curl http://<100.x>:3000/` with a forged `Host: *.ts.net`, `X-Forwarded-For: 100.64.0.1` and `Tailscale-User-Login: <admin>`. Next keeps a client-supplied XFF, so `header-trust.ts` accepted it and the peer became admin. The same path exposed tailscaled's health endpoint on `127.0.0.1:9002`. (2) Medium: PIN lockout and the per-IP limit were checked before a slow `argon2.verify`, and the attempt was recorded after it, so a concurrent burst got every guess verified. (3) Low: `sqlGuard` didn't check quoted function names (`"set_config"(…)`, `"query_to_xml"('select …')`), allowed `U&"\0070g_roles"` (= `pg_roles`), and allowed `repeat('x', 4e8)` across 600 rows, which could OOM the web process. (4) Low: `sql_query` results were redacted only on known column names, so `SELECT memo AS m` sent raw digits to the model. (5) Low: CSV export allowed formula injection.
- **(1) Network, defence in depth:**
  - **Kernel networking:** `TS_USERSPACE=false`, `devices: /dev/net/tun`, `cap_add: NET_ADMIN, NET_RAW` (NET_RAW as in Tailscale's Docker guide). No sysctls: the node doesn't route or act as an exit node, and Tailscale's docs list none for this case. In kernel mode, a packet to `100.x:3000` is never delivered to a socket bound to loopback. The health endpoint stays on `127.0.0.1:9002`; the image default is `[::]:9002`.
  - **Dedicated loopback alias:** Next.js binds `HOSTNAME=127.0.0.2`. Linux routes all of 127.0.0.0/8 to `lo`, so no setup is needed, and netstack only ever dials 127.0.0.1 or ::1. `serve.json` proxies to `http://127.0.0.2:3000`. Header trust now requires `HOSTNAME === HOMEBASE_LISTEN_HOST` (default `127.0.0.2`), and that value must be a 127/8 address other than 127.0.0.1. Binding 127.0.0.1, ::1, localhost or 0.0.0.0 turns trust off. So even if userspace mode came back, a raw tailnet connection can't reach the socket that trusts headers.
  - **Healthchecks:** the Dockerfile HEALTHCHECK and `deploy.sh` now probe `$HOSTNAME:$PORT`. Nothing listens on 127.0.0.1:3000 in production, on purpose. CI asserts `HOSTNAME=127.0.0.2`, `HOMEBASE_LISTEN_HOST=HOSTNAME`, `TS_USERSPACE=false`, a loopback health address, and the Serve proxy target.
  - **Local dev:** macOS only configures 127.0.0.1 (binding 127.0.0.2 fails with `EADDRNOTAVAIL`), so dev stays on 127.0.0.1 with trust off (the default). `src/server/identity/listen-host.test.ts` checks the bind on Linux (CI, and the container): it serves on 127.0.0.2 and refuses connections on 127.0.0.1 and ::1. It skips on macOS. Next standalone's `server.js` passes `process.env.HOSTNAME` to `listen()`.
  - **Tailnet policy (docs/server-setup.md 5a, spec §4.3):** the allow-all's `dst` narrows from `*` to `autogroup:member`. User-owned devices keep their access, but it no longer covers tagged nodes. An explicit grant lets `group:household` reach `tag:homebase` on `tcp:443` only, and policy `tests` assert that 443 is accepted and 80, 3000 and 9002 are denied. Grants only add up, so the old "add, don't replace" plan left every port open.
  - **Consequence:** in kernel mode, processes in the netns can now dial other tailnet devices. Homebase doesn't. A tagged source is still matched by `src: ["*"]`; narrowing that to `autogroup:member` is a later lockdown decision (§16).
- **(2) PIN race:** the stores gained `reserve(…, gate)` and `complete(id, success)`. `reserve` reads the user's history and the IP count, lets the policy veto, and otherwise inserts a **pending** attempt row that already counts as a failure. It does all of this in one step, serialized by a transaction-scoped advisory lock (`lockPinAttempts`, core) in the DB store, or synchronously in the memory store, and **before** argon2 runs. A match flips the row to success. A crash mid-verify leaves a failure, so it fails closed. `signInWithPin` also takes a per-user in-process mutex (on `globalThis`). Core gained `reservePinAttempt` and `completePinAttempt`, and `recordPinAttempt` now returns the id. Tests: 50 concurrent wrong PINs → exactly 5 verifications, then lockout (memory and Postgres stores); the DB reservation alone, without the mutex, grants exactly 5 slots; without the advisory lock the same core test granted 7.
- **(3) SQL guard and executor:**
  - **Guard:** the function denylist now also applies to every quoted identifier. Quoted function calls (`"x"(…)`) are refused outright, and so are `U&'…'` and `U&"…"`. The list gained `repeat`, `lpad`, `rpad`, `format` (width specifiers), `array_fill`, `ts_stat`, `ts_rewrite` (both run a SQL string), `crosstab*` and `connectby`. It already had `query_to_xml*`, `set_config`, `current_setting` and `pg_*`.
  - **Executor (`DbReadOnlySqlExecutor`):** it first runs `LIMIT 0` to get the column names and types without executing the query. It refuses more than 64 columns. It then wraps the query as `… AS hb_cap(c1…cn)` so each cell is capped server-side: text over 4,096 chars is cut and marked `…[truncated]`, and any other value larger than that becomes NULL. That way no single DataRow is large. Rows come through a `DECLARE … CURSOR` in batches of 50, stopping at about 2 MB (`truncatedBytes`), with one time budget across the FETCHes.
  - **Not done:** `REVOKE EXECUTE … FROM homebase_ro` would have no effect, because those functions are granted to PUBLIC. Revoking from PUBLIC would also hit the app role and live in pg_catalog ACLs across dumps and restores, and the guard plus the executor caps already cover it.
- **(4) Redaction:** `runGuardedSql` masks every 4+ digit run in every string value, deeply for json and arrays, whatever the column is called. It skips columns the executor reports as numeric, date/time, uuid or bool (by type OID), and strings that are entirely an ISO date, month or timestamp, or a uuid. Numbers stay numbers. The residual risk is a model that casts text to a number (`regexp_replace(memo,'\D','','g')::bigint`); the 8-digit safety net in `toModelJson` still applies to strings.
- **(5) CSV:** text cells starting with `=`, `+`, `-`, `@`, tab or CR get a leading `'`. Money (bigint) and number cells are rendered as numbers and never prefixed, and neither is a string that is just a signed decimal (`-12.50`).

## 2026-10-23 · Engine: golden parity run against the real YNAB export (§6.9)
- **Result:** with the defaults below, every month from the plan's first month through the last closed month matches exactly. That covers each category's assigned, activity and available, plus month `to_be_budgeted` and `goal_under_funded` in the snapshot month. The only differences left are in the open month (E13).
- **E12 Card lines categorized to Ready to Assign are debt-only** (`cardRtaLines: "debt_only"`, new default). **Verified:** YNAB's month `income` and `to_be_budgeted` exclude credit-account transactions categorized to "Inflow: Ready to Assign" (statement credits, balance adjustments, refunds sent to RTA), in both directions. They don't touch the payment category either; they only change the card's debt. That matches YNAB's note that a balance adjustment categorized to RTA "won't change the amount available in the payment category". The part of such an inflow that pushes the card above zero still reaches RTA as "Inflow from Debt Account" (E6; not exercised by the export). A card's uncategorized positive starting balance follows the same path. `cardRtaLines: "income"` restores the old behavior.
- **E13 Open-month residual (not resolved).** In the month the export was taken, both card payment categories differ by an equal and opposite amount. Their sum, every spending category, and RTA all match. That month is the only one with unapproved transactions, which are still being imported.
  - Re-ordering approved and unapproved transactions, or card order within a category, closes most of the gap but never all of it.
  - Analysis shows no per-transaction funding rule over the exported data can reproduce YNAB's split. Even funding every spending-category card purchase on one card falls short, and uncategorized card spending can't be funded without changing next month's RTA, which matches.
  - So YNAB's split for the open month appears path-dependent: computed incrementally as transactions arrive or are approved.
  - The golden test reports these rows but doesn't fail on them when, per month and field, the payment-category differences net to zero. Anything else is still fatal. `HOMEBASE_GOLDEN_STRICT=1` makes them fatal.
  - **Next step:** re-export after the month closes and everything is approved. If the difference persists in a closed month, compare YNAB's Credit Spending breakdown in the inspector for the affected categories.

## 2026-10-26 · Buckets: overflow (rollover)
- **Why:** Alex wants some buckets, spending money most of all, to save up month after month: if money is left at the end of a month, next month's goal goes up by that much until it is spent down again. It is a per-bucket option, off by default.
- **Columns (migration `0003_rollover`, generated by drizzle-kit):** `categories.rollover boolean NOT NULL DEFAULT false`, `categories.rollover_from date NULL` (the first month that counts; set to the current month when it is turned on), `categories.rollover_opening_milli bigint NOT NULL DEFAULT 0` (an optional amount carried into that first month, e.g. what is already saved). The `Category` type picks them up (`rollover`, `rolloverFrom`, `rolloverOpeningMilli`). The YNAB engine, its cache and Available are unaffected: this is a Budget-screen rule only.
- **Math (pure, `packages/core/src/buckets/math.ts`, also in `@homebase/core/buckets`):** carryIn(from) = max(0, opening); for each later month M, carryIn(M) = max(0, budget(M−1) − spent(M−1)) with budget(M) = monthlyGoal(M) + carryIn(M). Overspending never carries forward (the floor is 0); refunds (negative spent) leave more behind. Months before `rollover_from`, and buckets with rollover off, have no carry. `rolloverSchedule({from, opening, through, goalFor, spentFor})` gives the month-by-month walk, `rolloverCarryIn(settings, month, goalFor, spentFor)` the carry into one month, `goalInEffect(history, month)` the target row in effect (latest `effective_from` ≤ month, null when removed) and `monthlyGoalFromHistory(history, month)` that month's plain monthly goal through `monthlyGoalAmount`, so goal changes over time (targets history, weekly goals with 4 or 5 weekdays) count per month.
- **Choices made:** savings (balance) goals add nothing to the carry and never show one (their amount is a balance, not a month's money). A month with no goal (removed) adds 0 but the carry stays and drains with spending; such a row's budget is the carry alone and it counts as monthly money in the totals. Percent-of-income goals add 0 in earlier months (the engine's `needed` is only read for the month on screen). Turning it off keeps `rollover_from` and the opening as history but stops the carry; turning it on again starts fresh (this month, opening 0) unless a month or amount is given. Sending "on" while already on keeps the month and only changes what is given (that is how "Already saved" is edited).
- **Read model (`getBucketMonth`):** `BucketRow` gains `rollover`, `rolloverFrom`, `carryIn` and `goalAmount` (the plain monthly goal); `budget` is now goalAmount + carryIn, so the bar, `remaining`, the group totals and the summary ("$X left of $Y", pace) include the carry. The carry is computed from two queries regardless of history length: the target rows of rollover buckets up to last month, and `spentByCategoryMonth(db, from, to, ids)` (spent per category per month in one GROUP BY, the same rules as `spentByCategory`, which now shares its SQL). `rolloverCarries(db, month)` returns carryIn per rollover bucket.
- **Write:** core `setBucketRollover(ctx, categoryId, { enabled, openingMilli?, fromMonth? })`, a `category_edit` operation (`enable_rollover` / `disable_rollover`): audited (`budget.enable_rollover`) and undoable through row changes like the other category edits. Normal categories only; the opening can't be negative. Web: `setBucketRolloverAction` in `server/actions/glow.ts`.
- **UI:** the bucket sheet has an **Overflow** section (not for savings goals): a switch "Roll leftover money into next month" with one line of explanation; in the month it starts, an optional **Already saved** amount (AmountInput) sets the opening; other months say "Rolling over since August 2026". Toggling is optimistic with an Undo toast. ## 2026-10-26 · Buckets: savings buckets
- **Why:** Alex wants buckets like Taxes, Emergency Fund and House Renovations that are not set aside automatically every month: "We just want to be able to assign it as money comes in." A savings bucket has no monthly goal; money is added (or taken out) whenever it arrives, and the balance carries over month to month.
- **Columns (migration `0004_savings_buckets`, generated by drizzle-kit):** `categories.bucket_kind text NOT NULL DEFAULT 'spending'` (`'spending' | 'savings'`) and `categories.savings_target_milli bigint NULL` (an optional target total). Savings buckets reuse the overflow columns: `rollover_from` is the start month and `rollover_opening_milli` the starting balance. The `Category` type picks them up (`bucketKind`, `savingsTargetMilli`). The YNAB engine is unchanged: a contribution is an ordinary assignment, so Ready to Assign and Available keep working on `/plan`.
- **Math (pure, `packages/core/src/buckets/math.ts`, also in `@homebase/core/buckets`):** from `from` on, carryIn(from) = max(0, opening); contributed(M) = that month's `month_assignments` (negative = taken out); balance(M) = carryIn(M) + contributed(M) − spent(M), with spent the same net outflow as every bucket (refunds reduce it); carryIn(M+1) = max(0, balance(M)). A month's balance can go below zero after overspending, but the negative part never carries. Months before `from` don't count (everything 0, `started: false`). `savingsSchedule(settings, through, contributedFor, spentFor)`, `savingsMonth(...)`, `savingsProgress(balance, target)` (balance ÷ target in [0, 1], null without one), `savingsChangeError(balance, amount)`; `BucketKind`, `SavingsSettings`, `SavingsMonth`.
- **Read model:** `buckets/savings.ts`: `savingsSettings(db, ids?)`, `savingsMonths(db, month, settings?)` (assignments and spending since the earliest start in two queries), `savingsContributions(db, categoryId, month)` (this month's adds and take-outs from `budget_operations`, newest first, undone ones left out). `buckets/spending.ts` now holds `spentByCategory` / `spentByCategoryMonth` (re-exported from `month.ts`) so the write path can read balances without an import cycle through `budget/view`. `getBucketMonth`: every `BucketRow` has `bucketKind` and `savings` (`{balance, contributed, spent, carryIn, target, progress, from, opening, started}` or null). Savings rows are **not** in `groups`, the group totals or the summary (`totals`, `pace`); they come back in `BucketMonth.savings` `{rows, totalSaved, addedToSavings}`. `BucketMonth.income` is the engine's income for the month (inflows to on-budget accounts categorized to Ready to Assign / Income).
- **Writes (core, audited, undoable):** `setSavingsBucket(ctx, categoryId, { enabled, openingMilli?, fromMonth?, targetMilli? })` (`category_edit`, `enable_savings` / `disable_savings`): on sets `bucket_kind`, the start month (the current month unless given; kept when already savings), the starting balance (0 unless given; kept when already savings, which is how the sheet edits it), turns overflow off, and removes the goal from the start month on (goal rows later than that are dropped, the one in effect gets a `removed` row) so it never counts as spending money; a balance goal's amount becomes the target unless one is given.
